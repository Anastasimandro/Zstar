# Metadata streaming: 100,000 and 1,000,000 files, before and after

Task: replace the whole-tree `Vec<SourceEntry>` with a streaming walker feeding a bounded
queue, store the ZIP extraction plan compactly, and add explicit limits (ADR 0011, Part 2).
"Before" is commit 29fbc8c, "after" is the working tree of the commit that adds this file.

## What was measured, and how

- **Machine**: a 2-vCPU cloud VM, ext4-like file system, warm page cache, no `drop_caches`.
  Not a laptop, not an HDD, not Android. The VM was moved to a different host (kernel build
  v236 to v242) between the first full "after" run and the later paired runs, and ran 1.5 to 3
  times faster after it. **Comparisons are therefore only made inside one paired run**, where
  both binaries alternate on the same machine state; numbers from different runs are never
  compared with each other. The first matrix is kept in the data only for the figures that do
  not depend on speed (memory, allocation counts, order of magnitude).
- **Harness**: `crates/core/examples/meta_bench.rs` (one operation per process, so `VmHWM` is
  the peak RSS of that operation alone) driven by `scripts/meta-bench.sh`. The harness is
  copied into the old tree to measure "before", so both sides use the same code to measure.
- **Allocation count**: `scripts/alloc_count.c`, an `LD_PRELOAD` shim counting `malloc`,
  `calloc`, `realloc` and `aligned_alloc` calls (no `unsafe` Rust needed). It slows the run, so
  only the count is used from those runs. Python is not instrumented.
- **Time to first progress**: the first call of the progress callback, from the start of the
  operation. **Cancellation latency**: from `Control::cancel()` (timer thread, 400 ms after the
  start for 100k sets, 1500 ms for 1M) until the operation returns `Cancelled`.
- **Data sets** (generated by `scripts/meta-bench.sh gen`): `flat100k` and `flat1m` (all
  files in one directory, zero bytes), `tree1m` (1,000 directories x 1,000 zero-byte files),
  `tiny100k` (100 directories x 1,000 files of 64 bytes).
- **Repetitions**: 3 for the 100k sets, 2 for the 1M sets, 3 for cancellation. Medians
  unless a list is shown. Peak RSS is the maximum of the repetitions.
- **Archives are identical**: zip and tar.gz of all four sets (including both 1M sets) made
  by the new binary are byte for byte equal (`cmp`) to those made by the old one; zip, 7z, tar
  and tar.gz of a small mixed tree (nested directories, empty directory, empty file, symlink,
  random and compressible data, one thread) are equal too.

Reading:

- **tar.gz** needs nothing proportional to the number of entries any more: 28 MiB and 7 MiB
  against 449 and 304 MiB at 1M entries (the 28 MiB of `flat1m` is the names of the one
  directory, kept so that siblings can be sorted).
- **zip** halves peak RSS but still grows with the entry count: about 230 to 260 bytes per
  entry at 1M. That is the zip writer, which must keep each entry's record until it writes the
  central directory. Out of scope here; `--max-metadata` counts it (name, link target and 128
  bytes per entry) so it cannot grow without a limit.
- **7z** is unchanged by design: its writer needs all entries before the first byte, so the
  stream is drained into a list (and charged to the metadata limit). The 7z wall time is within
  1 to 5% of before; first progress is not better.
- **Time to first progress** goes from seconds (the whole tree was walked and stat'ed first)
  to milliseconds. In `flat1m` it is 311 to 355 ms because one directory is listed and sorted
  as a whole before its first entry; that is the bound of "siblings sorted per directory".
- **Wall time** is the same or better, with one honest exception: a first version of the
  queue handed over one entry per message and cost **+20%** on 100k files (zip 2.75 vs 2.27 s,
  7z 1.96 vs 1.53 s; tar.gz was faster than before even then). Entries now travel in batches of
  128; the table above is the batched build. The remaining +1 to +5% on zip and 7z (2.27 -> 2.29,
  2.28 -> 2.39, 1.53 -> 1.60 s) is inside the spread of the repetitions but is probably real
  and is the price of a second thread on a 2-vCPU machine.

## Extraction

Extraction of tar.* does not use the walker, and its code did not change apart from the new
name limits: memory (4 MiB at 1M entries) and allocation counts are identical before and after.

ZIP extraction (plan stored compactly):

| set | peak RSS MiB, before -> after | first progress ms, before -> after | alloc calls (M) |
|---|---|---|---|
| flat100k | 59 -> 43 | 122 -> 74 | 1.60 -> 1.90 |
| tiny100k | 57 -> 44 | 129 -> 89 | 1.70 -> 2.10 |
| flat1m | 568 -> 405 | 3,064 -> 1,149 | 15.00 -> 17.00 |
| tree1m | 582 -> 409 | 3,516 -> 1,537 | 17.01 -> 21.01 |

- **Memory** falls by about 30%, not to a constant: what remains at 1M entries (about 400 MiB)
  is the `zip` crate's own copy of the central directory, one per worker thread. Reaching it
  needs a reader shared between workers or a different crate version: Task 3.
- **Allocations rise** by 13% to 23% because paths, modes and times are derived again when an
  entry is extracted (the same checks run twice, deliberately, rather than keeping a
  `PathBuf` and a `String` per entry). The user CPU time does not rise: 0.49 -> 0.38 s on
  `tiny100k` (median of 4) and 5.58 -> 4.93 s on `tree1m` (2 runs).
- **Wall time cannot be compared on this VM.** The same binary takes 5.3 s or 24 s for
  `flat100k`, and 94 s or 141 s for `tree1m`, depending on the state of the kernel (nearly all
  of it is system time creating files: 110 to 120 of 116 to 125 CPU seconds on `tree1m`).
  Paired runs gave before/after of 6.7/23.0 s (`flat100k`), 8.8/8.6 s (`tiny100k`), 81/144 s
  (`flat1m`) and 102/141 s (`tree1m`): the slow mode landed more often on the "after" runs but
  both binaries showed both modes, so no change in wall time is claimed, in either direction.
  A real disk or a quiet machine is needed to resolve it.

## Cancellation

Median and maximum of 3 runs, milliseconds from `cancel()` until the operation returns.

| operation | set | before | after |
|---|---|---|---|
| create zip | flat1m | 3,039 (max 3,213) | 5 (max 6) |
| create zip | tree1m | 3,118 (max 3,328) | 6 (max 7) |
| create zip | flat100k / tiny100k | 14 (max 2,470) / 28 (max 1,450) | 1 (max 55) / 2 (max 2) |
| extract zip | flat1m | 1,156 (max 1,216) | 58 (max 65) |
| extract zip | tree1m | 422 (max 463) | 65 (max 65) |
| extract zip | flat100k / tiny100k | 22 / 23 | 6 / 6 |

Before, creation could not be cancelled while the tree was being walked, so a request made in
the first seconds waited until the walk ended. Now the walker checks the flag per entry and
every 1,024 entries of a directory listing, and the format checks it per entry.
(The 100k figures are from the first matrix, before batching; the 1M creation figures are from
the batched build.)

## What was not measured

- A hard disk, an SSD or NVMe with cold cache, Windows, macOS or Android. Everything is warm
  cache on a VM; the effect of fewer `stat` calls ahead of the first write is not measured.
- Extraction wall time (see above), 7z allocation counts, and any file system other than the
  VM's.
- Archives with very long names or very deep trees at scale: those paths are covered by tests
  (`crates/core/tests/meta_limits.rs`), not benchmarks.
